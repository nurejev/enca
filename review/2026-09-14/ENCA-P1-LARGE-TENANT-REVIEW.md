# ENCA: every-tool review for P1, large tenants and responsive feedback

**Reviewed:** 14 September 2026 · **Branch:** beta · **Commit:** `b2bbfd2` · **Build:** 25363.

**Recommendation:** make ENCA's core fully usable on Entra ID P1, with clearly identified optional capabilities for additional products. Fix incomplete-result handling and inconsistent policy evaluation before promoting the reviewed build for broad large-tenant use. Improve the shared reader and progress display before optimizing individual screens.

This is an advice-only review. No application code, tenant configuration, release metadata or deployment was changed. It covers all **40 permanent tool IDs**, including capabilities now folded into another tool. It combines source review, Microsoft Learn verification, the existing regression suite, targeted offline reproductions and synthetic processing measurements. It is **not** certification from running all tools against licensed production tenants.

## 1. What “P1 and up” should mean

Every core workflow must open and produce its supported P1 result without requiring P2, Defender, Intune or Governance consent. An optional evidence source must not prevent the supported result from loading. P2 is not a universal bundle of the other products.

## 2. Findings to address first

Severity below means implementation priority: **High** blocks a trustworthy result in the affected workflow; **Medium** requires hardening for the promised scale or support level. “Reproduced” uses mocked/local inputs, never tenant writes.

### F00 — High: group recreation can retarget policies after membership-copy failure

**Reproduced with mocked reads and writes.** `moveGroupMembers` catches a failed source-membership read and substitutes an empty array. The disable-nesting recreation flow then continues to repoint policies at the new group. The fixture returns a 403 for membership, copies zero members, records zero failures and still patches a policy to the replacement group. Individual copy failures are also recorded without stopping that reference-switch loop.

This can remove an intended inclusion or exclusion from affected users. Make a complete source read and verified destination membership mandatory before changing any policy reference. If copying fails, keep the old policy references intact, report the staged replacement and allow a controlled retry. This shared helper also serves other group-recreation/import-copy paths, so the gate belongs in the shared workflow. Test partial copy, unread source, nested members and destination readback failure.

Evidence: [member-copy helper](/Users/mihaimonte/REPO/enca/js/app.js:6037), [policy reference switch](/Users/mihaimonte/REPO/enca/js/app.js:6555), [import counterpart copy](/Users/mihaimonte/REPO/enca/js/app.js:3476).

### F01 — High: a capped read can be labelled complete

**Reproduced.** `makeProgress.fetchAll` sets `capped` only from `@odata.nextLink`, then slices to the cap. A final page containing 600 members with a 500-member limit returns 500 and `capped: false`. T37 takes that flag directly. A global completeness badge can therefore be wrong even without a network failure.

Fix the pager contract to return returned count, observed count, truncation reason and continuation separately. Cutting off rows already received must count as truncation. Test 499/500/501/600 rows, with and without a next link, plus an empty intermediate page.

Evidence: [app.js:10873](/Users/mihaimonte/REPO/enca/js/app.js:10873), [T37 member read](/Users/mihaimonte/REPO/enca/js/app.js:16042).

### F02 — High: wave membership gaps can become definite policy decisions

**Source-confirmed; decision difference reproduced.** T37 reads only the first 999 users of referenced groups; failed batch entries are omitted. `Wave.analyze` treats a user absent from those sets as not belonging. An exclusion member on a later page is consequently shown as included in the policy. The referenced-group truncation banner does not correct the individual verdict. Role membership is also first-page only, without expanding users behind role-assigned groups. Parent-group read failures are swallowed.

Use one shared, complete membership resolver. Propagate unknown scope to each affected cell, count and readiness decision. Do not recommend activation when the required inclusion/exclusion evidence is unknown. Child-group explanations also need explicit coverage for their 40-group/first-page limits.

Evidence: [app.js:15999](/Users/mihaimonte/REPO/enca/js/app.js:15999), [role reads](/Users/mihaimonte/REPO/enca/js/app.js:16072), [wave.js:75](/Users/mihaimonte/REPO/enca/js/wave.js:75).

### F03 — High: Compare users disagrees with the shared scope engine

**Reproduced.** T18 retains its own scope logic. A guest from the wrong external type/tenant is marked included because `includeGuestsOrExternalUsers` becomes a boolean. Conversely, the legacy `GuestsOrExternalUsers` token is missed. Both results disagree with `CaScope`. The scenario renderer also chooses the green/grant style from `blocked` without checking `complete`; indeterminate scenarios can look conclusive.

Move T18 onto the shared scope engine and carry unknown outcomes through the comparison, What-If table and Markdown export. Reuse the guest/type/tenant and unsupported-condition fixtures already protecting other tools.

Evidence: [compare.js:64](/Users/mihaimonte/REPO/enca/js/compare.js:64), [scenario assembly](/Users/mihaimonte/REPO/enca/js/compare.js:107), [app.js:15589](/Users/mihaimonte/REPO/enca/js/app.js:15589).

### F04 — High: exclusion totals discard data already downloaded

**Reproduced.** T09 fully downloads group members, stores the total, but retains only the first 500 for `effectiveUsers`. The fixture reads 600 and reports only 500 effective users. Disabled-member counts and per-user exports inherit that sample. The UI may show the group total, but the per-user result is still incomplete. T12 uses a similar full-read/500-row retention pattern and needs an explicit presentation-versus-analysis boundary.

Retain complete membership for computation, or aggregate it as pages arrive. Apply the display limit only at rendering. Mark every sampled result and export with its coverage; never label a sampled effective-user list a full result.

Evidence: [exclusions.js:173](/Users/mihaimonte/REPO/enca/js/exclusions.js:173), [effectiveUsers](/Users/mihaimonte/REPO/enca/js/exclusions.js:266), [cagroups.js:650](/Users/mihaimonte/REPO/enca/js/cagroups.js:650).

### F05 — High: changing log source during a read mislabels the result

**Reproduced.** `readSignInWindow` starts using the selected source, then writes the cache using the current global `logSource` after awaiting the result. Starting an Entra read, switching to hunting, and completing the original read stores Entra rows as hunting rows.

Capture an immutable run context: tenant/account, source, API version, event type, range, filters and policy revision. Publish only if that context is still valid. Scope shared caches and in-flight joins to it. Test source, tenant, range and sign-out changes during a delayed read; only the source-change failure was reproduced here.

Evidence: [app.js:12959](/Users/mihaimonte/REPO/enca/js/app.js:12959).

### F06 — High: Azure reads throw after a successful response

**Reproduced.** `armFetch(url, init)` references an undefined `opts` variable while deciding whether a request is retryable. A mocked 200 response produces `ReferenceError: opts is not defined`. This affects the Azure portion of T19 and shared ARM consumers, including self-host configuration.

Correct the variable and add ARM-specific tests for successful GET, read-only Resource Graph POST, PATCH, 429 and ambiguous write failures. Existing Graph tests do not cover this path.

Evidence: [graph.js:254](/Users/mihaimonte/REPO/enca/js/graph.js:254).

### F07 — High: failed object reads can become “not found” findings

**Reproduced for T19.** A 403 from the CA-referenced group lookup is caught, after which all unresolved IDs become `missing: true`. That makes an unreadable group look deleted. T19's inherited-scope read also catches errors and proceeds without parent memberships. T31's role-assigned-group expansion stops at its page limit without propagating truncation into the role result.

Distinguish a successful lookup that did not return an object from an unsuccessful lookup. Preserve per-source/per-object coverage and retry only the failed portions. Any “unused,” “dangling,” “not targeted” or exact licence-count conclusion must depend on complete supporting reads.

Evidence: [app.js:16670](/Users/mihaimonte/REPO/enca/js/app.js:16670), [groupuse.js:713](/Users/mihaimonte/REPO/enca/js/groupuse.js:713), [app.js:12310](/Users/mihaimonte/REPO/enca/js/app.js:12310).

The same failure-to-empty pattern is source-confirmed in T16's membership audit stream, T21's strengths/locations reads and T24's deleted-location read. These need explicit per-source failure states too. [Audit read](/Users/mihaimonte/REPO/enca/js/app.js:10952), [CIS reads](/Users/mihaimonte/REPO/enca/js/app.js:17697), [recycle read](/Users/mihaimonte/REPO/enca/js/app.js:15034).

### F08 — Medium: P1 users are unnecessarily steered to hunting for non-interactive events

The source picker describes Graph as interactive-only and claims it never returns non-interactive sign-ins. Microsoft documents explicit `signInEventTypes` filtering on the beta sign-in API, including non-interactive user events, and lists P1/P2 access. The current Entra query does not request that event type.

Add a separately labelled, tested Graph option for non-interactive user events. Because the documented route is beta, expose its preview status and preserve the stable interactive P1 path. Do not imply service-principal and managed-identity events share the same licensing, fields or policy semantics. Remove the unconditional “no cap” hunting claim: the recursive reader still has minimum-slice limits.

Evidence: [source picker](/Users/mihaimonte/REPO/enca/js/app.js:12777), [Graph query](/Users/mihaimonte/REPO/enca/js/reportimpact.js:28), [Microsoft sign-in API examples](https://learn.microsoft.com/graph/api/signin-list?view=graph-rest-beta#examples).

### F09 — Medium: the common wait display can look stuck or falsely finished

**Reproduced.** Before the first page, the text hides elapsed time even after 30 seconds. T33 starts progress with a 25-page cap but ticks user counts; 999 users on page one produces a 100% bar. Elsewhere a record safety cap is used as if it were a known total. Phase starts reset the clock, so overall duration is lost. Most shared progress instances do not expose Stop.

Use an indeterminate bar when total work is unknown, a persistent run clock from the click, and completed-items progress only when the denominator is known. Show the current phase and last successful response independently. Render results from the first useful page, not after five pages. The detailed proposed behaviour is in section 5.

Evidence: [app.js:10821](/Users/mihaimonte/REPO/enca/js/app.js:10821), [T33 progress](/Users/mihaimonte/REPO/enca/js/app.js:18655), [five-page partial callback](/Users/mihaimonte/REPO/enca/js/app.js:12977).

### F10 — Medium: batch retry truncates Microsoft's wait instruction

**Reproduced.** A batch subresponse with `Retry-After: 120` schedules only 60 seconds before retry. That can prolong throttling in large tenants. Keep the existing bounded retries and protection against blindly retrying ambiguous writes, but honour the full server delay. Display a persistent countdown with the affected operation and cancellation control.

Evidence: [graph.js:354](/Users/mihaimonte/REPO/enca/js/graph.js:354), [Microsoft throttling guidance](https://learn.microsoft.com/graph/throttling#throttling-and-batching). Batching combines up to 20 requests; it does not bypass their individual throttling limits. [JSON batching](https://learn.microsoft.com/graph/json-batching).

### F11 — Medium: large reads and local analysis need different execution strategies

The policy cap is small compared with user/group/log volumes. The main costs are membership expansion, full-directory enumeration, repeated aggregation, large result structures and DOM rendering. T37 additionally searches each member's policy states repeatedly while building each policy summary, producing an avoidable users × policies² pass. T03's bypass comparisons can also grow beyond a simple users × policies pass.

Start with narrow scopes, shared paginated reads and incremental aggregates. Move heavy pure analysis to a worker; use indexed maps for policy/member joins and paginated or virtualized result tables. Do not merely increase the 10,000-sign-in or 500-member caps. Preserve complete export semantics independently of visible rows.

Evidence: [analyze.js:261](/Users/mihaimonte/REPO/enca/js/analyze.js:261), [wave.js:148](/Users/mihaimonte/REPO/enca/js/wave.js:148), [reportimpact.js:154](/Users/mihaimonte/REPO/enca/js/reportimpact.js:154), measurements in section 4.

### F12 — Medium: P1 compatibility and endpoint support need a common preflight

The importer has a workload-identity licence check, and CIS already has some P2 gating, but there is no single feature-level contract shared by import, fixes, state changes and guided rollout. The default Graph base is beta. Microsoft advises using v1.0 for supported production APIs; beta behaviour can change.

Create an endpoint/capability inventory with version, minimum product, scopes, operator role, pagination and fallback. Use v1.0 where it preserves required fields; isolate beta-only features rather than changing the base globally. Before import, show incompatible policies, unresolved dependencies, required entitlements and available policy slots. The current limit is 240 across all states: replacement imports that stage a new policy need temporary headroom. Never silently remove a premium condition to make a policy fit P1.

Evidence: [authConfig.js:40](/Users/mihaimonte/REPO/enca/js/authConfig.js:40), [import.js:55](/Users/mihaimonte/REPO/enca/js/import.js:55), [CIS gating](/Users/mihaimonte/REPO/enca/js/app.js:17697), [beta API guidance](https://learn.microsoft.com/microsoft-cloud/dev/dev-proxy/concepts/use-microsoft-graph-beta-production), [240-policy limit](https://learn.microsoft.com/entra/identity/conditional-access/plan-conditional-access#recommendations).

## 4. Large-tenant performance findings

### Measured processing, not tenant response time

Synthetic fixtures ran on the local **darwin/arm64 host with Node v24.17.0**. These measure the real pure analysis functions with in-memory test data. They exclude authentication, Graph latency, downloads, DOM rendering and exports. Three runs are summarized by their median except Analyzer, which was measured once per size. They are indicative and not browser p95 service-level measurements.

| Function             | Fixture                                                              | Processing time   |
| -------------------- | -------------------------------------------------------------------- | ----------------- |
| `Wave.analyze`       | 100 users × 50 policies                                              | 3.7 ms median     |
| `Wave.analyze`       | 500 users × 100 policies                                             | 47.3 ms median    |
| `Wave.analyze`       | 500 users × 200 policies                                             | 157.8 ms median   |
| `ReportImpact.build` | 10,000 sign-ins, 10 report-only policies/event, 1,000 distinct users | 44.0 ms median    |
| `ReportImpact.build` | 100,000 sign-ins, same policy/user shape                             | 266.4 ms median   |
| `Analyzer.evaluate`  | 1,000 users × 100 policies                                           | 73.3 ms, one run  |
| `Analyzer.evaluate`  | 5,000 users × 100 policies                                           | 356.5 ms, one run |
| `Analyzer.evaluate`  | 10,000 users × 100 policies                                          | 712.4 ms, one run |

The Analyzer fixture uses straightforward All-users MFA policies, without expensive bypass comparisons. ReportImpact uses successful evaluations and a limited number of distinct users. Neither is a worst case. The 100,000-event fixture intentionally exercises processing above the normal Entra UI cap; it is not evidence that the current Graph path retrieves that many records.

Even these modest inputs justify separating computation from rendering. Raising limits first would amplify both memory use and unresponsive periods. Network work is likely to dominate many real runs, but that remains to be measured.

### Network scale and coverage

At an assumed full page of 999, reading 250,000 users requires at least 251 pages. Expanding 100 groups of 10,000 users requires roughly 1,100 membership pages, before other lookups. These are planning calculations, not measured requests or promises of latency.

A 10,000-sign-in sample in a tenant generating one million events/day represents approximately **14.4 minutes at a uniform rate**, not the requested seven-day window. Actual distribution varies. The screen must show the interval covered by returned events and whether the full requested query completed.

Recommended implementation order:

1. One shared read layer returning data plus completeness, continuation, source, read time and errors; immutable run context and request deduplication.
2. Bounded concurrency by source/tenant with adaptive backoff. Use batching to reduce round trips, not as a quota bypass. Honour server delays fully.
3. Count or narrowly filter where supported; prioritize the selected user/group and visible section. Fetch expensive optional evidence on demand.
4. Process pages incrementally. Cache stable reference data separately from volatile membership/sign-ins, with explicit freshness and rescan.
5. Worker-based computation for large analysis, indexed joins, bounded examples and paginated/virtualized display. Avoid rebuilding whole tables on every progress tick.
6. Keep export completeness independent of rendering. For truly huge jobs, evaluate an opt-in resumable backend later, with explicit tenant/data handling; it is not necessary for the first P1 fixes.

## 5. What users should see while waiting

Use one shared pattern across all tools, consistent with the approved branding and layout. Keep the title, subject tabs, toolbar and result columns in stable positions. Load content inside reserved sections instead of replacing the whole screen with a differently sized prompt.

| Moment                                  | Proposed behaviour                                                                                                                                                                                                          |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Immediately after the click             | Acknowledge the action, keep controls stable, and prevent duplicate submission. Target visible acknowledgement within 100 ms.                                                                                               |
| When the operation exceeds about 300 ms | Show a spinner/indeterminate bar, phase label and elapsed time from the original click. These are proposed UX targets, not measured current guarantees.                                                                     |
| First useful page                       | Display provisional counts and rows. Label them “Reading continues” and retain their position as more data arrives. Do not wait for page five.                                                                              |
| While waiting on Microsoft              | Keep the elapsed clock moving and show last response time. A slow first response should say “Waiting for Microsoft's first response · 12s.”                                                                                 |
| During throttling                       | Show “Microsoft asked us to wait · retrying in 42s,” with attempt and affected source available in details. Keep prior results visible.                                                                                     |
| During CPU processing                   | Show “Evaluating 8,000 of 25,000 users”; run in a worker or yield in small chunks so the progress can actually paint.                                                                                                       |
| On Stop                                 | For reads, cancel the request where supported and retain explicitly partial results. For writes, stop at a safe item boundary and verify/report the current item; cancelling a client request does not undo a server write. |
| On source failure                       | Keep successful sections. Name the failed source and offer “Retry this section.” Do not replace unread counts with zero.                                                                                                    |
| On completion                           | Show complete/partial/stopped/failed status, counts, actual coverage, tenant/source, read time and elapsed duration. Export these facts too.                                                                                |

Example after the first useful response:

> **Reading group memberships** · 18s
> 12 of 48 groups complete · 8,412 members read
> Results below are provisional. Two groups are waiting for Microsoft.
> **Stop read** · **View results so far**

Only show an ETA when enough comparable work has completed to support it; display it as an estimate. Unknown totals need activity and counts, not a fabricated percentage. Keep overall elapsed time separate from phase duration. Add an accessible status region, avoid announcing every row or every clock tick, and respect reduced-motion preferences.

Suggested acceptance budgets on an agreed reference laptop: progress/status updates at least once per second while waiting, first useful results within one second of a page being received, no avoidable main-thread processing blocks over 50 ms during large analysis, and responsive Stop intent within 250 ms. These are proposed engineering targets; validate them in a real browser before calling them achieved.
